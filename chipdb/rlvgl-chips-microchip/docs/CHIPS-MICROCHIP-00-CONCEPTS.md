# CHIPS-MICROCHIP-00 — Microchip BSP Generator Concepts

**Status:** Ratified 2026-05-11 (owner: Ira Abbott; see §15).

The CHIPS-MICROCHIP family brings the `chipdb/rlvgl-chips-microchip`
crate to parity with the five vendor pipelines already shipping
(`rlvgl-chips-esp`, `rlvgl-chips-nrf`, `rlvgl-chips-nxp`,
`rlvgl-chips-rp2040`, `rlvgl-chips-renesas`). Today the crate is a
**stub**: it carries the same `BoardInfo` / `chip_yaml` / `board_yaml`
public surface as its peers, but only a single placeholder
`ATSAMD51J19A` YAML pair is committed, and the BSP generator side
(`src/bin/creator/bsp/microchip.rs`) is the *generic* `Ir` round-trip
shim rather than a vendor-specific IR + render pipeline. This concepts
doc is the source of truth for the vocabulary, frozen invariants, and
reconciliation decisions that subsequent `CHIPS-MICROCHIP-NN` PRs MUST
cite. It is the spec-before-code ratification that the CLAUDE.md
"Spec-Before-Code Planning Discipline" section requires before any
behaviour PR lands.

## 0. Authority policy

Microchip's portfolio spans products from three historical lineages
(Microchip Technology PIC8/PIC16/PIC18/PIC24/dsPIC; the former Atmel
megaAVR / tinyAVR / SAM line acquired in 2016; the former Microsemi
FPGA / SoC line acquired in 2018). The `CHIPS-MICROCHIP-NN` family
covers only a narrow slice of that portfolio (the **SAM Cortex-M
slice** — see §5 and §11); everything else is explicitly out of scope
in §11.

| Concern | Owner | CHIPS-MICROCHIP side relationship |
|---|---|---|
| Per-chip register layout, reset values, clock-tree topology, and pin multiplexer signal tables for SAM D / D5x / E5x / L / C parts | Microchip SAM-family Family Data Sheets / Reference Manuals (e.g. "SAM D5x/E5x Family Data Sheet" DS60001507; "SAM D21 Family Data Sheet" DS40001882; "SAM L21 Family Data Sheet" DS60001477) and per-chip Errata Sheets | Cited; not redocumented. Each `chipdb/rlvgl-chips-microchip/db/chips/<chip>.yaml` MUST include a `source:` block naming the family datasheet by DS-number + revision date, in the same shape ESP uses for TRM citations. |
| svd2rust-style Peripheral Access Crate (PAC) for the targeted chip | Upstream `atsamd-rs/atsamd` workspace; published crates `atsamd21j`, `atsamd51j20a`, `atsamd51g19a`, `atsamd51j19a`, `atsame54p20a`, `atsaml21j18b`, etc. (versions float; the chip YAML pins one). Each is generated by `svd2rust` from Atmel SVD packs. | Consumed as a pinned dependency. The `pac_crate:` and `pac_version:` keys in the chip YAML name the exact crate + minor version the generator emits against. CHIPS-MICROCHIP MUST NOT vendor a PAC; it generates *against* an upstream PAC the way `rlvgl-chips-esp` generates against `esp32c3 = 0.31`. |
| Board-level pinout (which SAM signal lands on which header pin, console UART selection, external crystal frequency) | Per-board user guides (e.g. "SAM D5x/E5x Xplained Pro User Guide", "Adafruit Feather M4 Express pinout sheet", "SparkFun SAMD51 Thing Plus hookup guide") | Cited in `chipdb/rlvgl-chips-microchip/db/boards/<board>.yaml` `source:` block. Pin assignments derive from the board user guide, not from the chip datasheet (the chip datasheet only knows which signals *can* land on which pad). |
| `cortex-m` / `cortex-m-rt` ABI, vector table layout, ARMv7-M instruction semantics | ARM Cortex-M0+ / Cortex-M4F Architecture Reference Manuals; the `cortex-m` crate (≥0.7) | Consumed via published APIs. CHIPS-MICROCHIP MUST NOT redocument architectural semantics; the generator emits `#[entry]` from `cortex-m-rt` and assumes the standard ARM exception model. |
| `rlvgl-creator` IR shape, MiniJinja template engine, file-emission contract | `src/bin/creator/bsp/ir.rs`, `src/bin/creator/bsp/espressif/render.rs`, the existing `template_set` machinery | CHIPS-MICROCHIP MUST consume these without modification. The reconciliation in §10 enumerates what the Microchip pipeline needs that the generic `Ir` does not currently model. |
| Workspace-wide `BoardInfo` API contract (`vendor()`, `boards()`, `find()`, `chip_yaml()`, `board_yaml()`, `raw_db()`) | `chipdb/rlvgl-chips-esp/src/lib.rs` (canonical reference); identical signatures across all five shipping vendor crates | Already met by the existing `chipdb/rlvgl-chips-microchip/src/lib.rs`. The stub satisfies §0 of this authority table today; behaviour PRs MUST NOT alter the public API surface. |

If a CHIPS-MICROCHIP-NN PR needs to **modify** a cited authority
(e.g. it discovers that the SAM D51 datasheet's `MCLK` clock-gate
table is wrong, or that a board user guide misnames a pin), the
correction lands as a §15 amendment to this doc **first**, with the
errata cite and the datasheet reference being amended, before the
behaviour PR rides on it. This mirrors the DCB §0 policy and the
CLAUDE.md "Execution discipline" requirement.

## 1. Purpose

Bring `chipdb/rlvgl-chips-microchip` from stub state to a working,
publishable vendor pipeline that:

- enumerates a meaningful slice of Microchip's SAM Cortex-M
  portfolio (chip count negotiated in CHIPS-MICROCHIP-01; minimum
  one chip + one board per the §12 acceptance gate);
- carries machine-readable chip + board YAML matching the ESP shape
  (memory map, clock tree, peripheral table, pad mux, board pin
  assignments) under `chipdb/rlvgl-chips-microchip/db/`;
- ships a vendor-specific `MicrochipIr` + render pipeline under
  `src/bin/creator/bsp/microchip/` paralleling
  `src/bin/creator/bsp/espressif/`, with six emission templates
  (`mod.rs`, `pac.rs`, `clocks.rs`, `io_mux.rs`, `peripherals.rs`,
  `board.rs`) plus the two linker-script templates (`memory.x`,
  `chip.x`) the ESP family ships;
- exposes a `bsp from-yaml --vendor microchip` CLI path in
  `rlvgl-creator` mirroring the ESP / NXP / Nordic / Renesas / RP
  invocations;
- gates output through snapshot tests (`tests/bsp_microchip_render.rs`)
  and an opt-in `compile-verify` test that materialises a throwaway
  cargo project around the generated files and runs `cargo check`
  against the real upstream PAC on `thumbv7em-none-eabihf` (Cortex-M4F
  parts) or `thumbv6m-none-eabi` (Cortex-M0+ parts).

This phase produces **no executable artifacts**. It establishes the
vocabulary that CHIPS-MICROCHIP-01 (the first behaviour phase) builds
on.

## 2. Problem statement

The five shipping vendor pipelines (`esp`, `nrf`, `nxp`, `rp2040`,
`renesas`) demonstrate that the chipdb-crate + vendor-IR + 6-template
pattern is the convergent shape for vendor BSP generation in this
repo. The Microchip crate today does **not** follow that pattern:

- **Chip YAML is a stub.** `chipdb/rlvgl-chips-microchip/db/chips/ATSAMD51J19A.yaml`
  contains only five keys (`name`, `arch`, `package`, `pac_crate`, and a
  comment). There is no `memory:` block, no `clock_tree:`, no
  `peripherals:`, no `io_mux:`. The ESP equivalent
  (`chipdb/rlvgl-chips-esp/db/chips/esp32c3.yaml`) is ~300 lines and
  covers every field a generator template references.
- **Board YAML is a stub.** `chipdb/rlvgl-chips-microchip/db/boards/ATSAMD51J19A.yaml`
  has `name`, `chip`, `flash_mb`, a `console:` block, and `pins: []`.
  No pin assignments. The ESP equivalent
  (`chipdb/rlvgl-chips-esp/db/boards/esp32c3_devkitm_1.yaml`) carries
  ~30 lines of pin entries with signal / direction / label / pull.
- **There is no MicrochipIr.** `src/bin/creator/bsp/microchip.rs` is
  18 lines of pass-through `serde_yaml::from_str::<Ir>(text)` against
  the generic IR. The ESP equivalent
  (`src/bin/creator/bsp/espressif/`) is a four-file module
  (`ir.rs`, `load.rs`, `render.rs`, `mod.rs`) plus eight templates
  carrying real svd2rust-style codegen for UART0-as-console + I2C +
  SPI master + LEDC + Timer Group, with all other peripherals stubbed.
- **There is no `bsp from-yaml --vendor microchip` CLI surface.** The
  CLI's vendor dispatch matches `esp`, `nrf`, `nxp`, `rp2040`, `renesas`,
  and a generic `stm` IOC path; `microchip` is not a registered vendor
  key on that command path.
- **No snapshot / compile-verify tests exist.** The five shipping
  vendors each have `tests/bsp_<vendor>_render.rs` and (for ESP at
  least) `tests/bsp_<vendor>_compile.rs` (opt-in `compile-verify`
  feature). The Microchip path has neither.

Every gap above is the kind of vocabulary drift CLAUDE.md
"Spec-Before-Code Planning Discipline" exists to prevent. The fix is
to ratify the shape **once**, in this doc, before any chip / board
YAML or template lands. CHIPS-MICROCHIP-01..NN execution PRs then
cite §5 / §6 / §7 / §8 / §10 / §12 by section number, and any
modification to a frozen invariant rides on a §15 amendment first.

## 3. Glossary

Reserved CHIPS-MICROCHIP vocabulary. Capitalised use of these terms
in CHIPS-MICROCHIP docs MUST refer to the defined meaning;
alternative phrasings introduce drift and are forbidden in
normative sections.

| Term | Meaning | Owner |
|---|---|---|
| **SAM** | The Atmel-lineage Microchip MCU family branding (formerly "SMART ARM-based Microcontrollers"). Sub-families include SAM D / D5x / E5x / L / C / G / V / S, all ARM-Cortex-M cores. CHIPS-MICROCHIP scopes to the SAM Cortex-M slice; non-SAM Microchip parts are out of scope per §11. | Microchip product taxonomy. |
| **SAM D-class** | The umbrella covering SAM D5x / E5x (Cortex-M4F at 120 MHz) and SAM D / SAM L / SAM C (Cortex-M0+ at 48 MHz). Used here to abstract over the part-number families when the distinction doesn't matter for IR shape. | This doc. |
| **PAC crate** | Per-chip svd2rust-generated peripheral access crate, published from `atsamd-rs/atsamd`. E.g. `atsamd51j19a` v0.13.x. The Microchip chip YAML's `pac_crate:` key names the crate; `pac_version:` pins the minor version. As defined in `chipdb/rlvgl-chips-microchip/db/chips/ATSAMD51J19A.yaml:5`; adapted: this doc adds the `pac_version:` key that the stub does not yet carry. | This doc; mirrors ESP's `pac_crate:` convention. |
| **GCLK** | Generic Clock Controller. The SAM D-class central clock multiplexer that selects one of N clock sources and divides it down to drive one or more peripheral generic-clock channels. Distinct from the PCM (Power Manager Channel) gate that controls APB / AHB clock distribution. | SAM D5x/E5x Family Data Sheet §15 (GCLK). |
| **MCLK** | Main Clock Controller (SAM D5x/E5x; the SAM D21 equivalent is **PM** — Power Manager). Owns the AHB and APBA/APBB/APBC/APBD bus clock enable masks. Asserting a peripheral's `MCLK.APBx_MASK` bit ungates its bus clock; the corresponding `GCLK.PCHCTRL` peripheral generic-clock channel ungates its functional clock. **Two-step gating** is normative for the SAM D-class — see §6 INV-MC1. | SAM D5x/E5x Family Data Sheet §16 (MCLK). |
| **PORT** | The SAM GPIO controller. Each pad is identified by a `(group, pin)` pair (`group` 0..3 = ports A..D; `pin` 0..31). Mux selection is via the `PMUX` register (4-bit selector encoding alternate functions A..H or N). The `PINCFG` register controls input-enable / pull / drive-strength bits. CHIPS-MICROCHIP's `io_mux.rs` template emits `PORT.GROUPx.PMUX` + `PINCFG` writes. | SAM D5x/E5x Family Data Sheet §32 (PORT). |
| **SERCOM** | The Serial Communication peripheral block — six (D5x) or five (D21) instances per chip, each runtime-configurable as USART / I²C master / I²C slave / SPI master / SPI slave. The `mode:` field on a SERCOM instance in chip YAML names which protocol the generator emits init code for. SERCOM mode IS the IR shape's source of asymmetry vs. ESP's fixed-role peripherals (where `uart0` is always a UART). | SAM D5x/E5x Family Data Sheet §34 (SERCOM). |
| **NVMCTRL** | The flash controller. The chip YAML's `memory:` block names the flash region size, but bring-up code does not currently touch NVMCTRL; only its wait-state count needs configuring as a function of CPU frequency. Captured in `clocks.rs` for the D5x line, per §7. | SAM D5x/E5x Family Data Sheet §25 (NVMCTRL). |
| **EIC** | External Interrupt Controller. Pin-routed interrupt source for the SAM D-class. Out of scope for CHIPS-MICROCHIP-01; the IR carries a placeholder field but emits no init code. Standards Action to extend. | SAM D5x/E5x Family Data Sheet §22 (EIC). |
| **MicrochipIr** | The vendor-specific intermediate representation produced by `src/bin/creator/bsp/microchip/load.rs` from the chip+board YAML pair. Parallels `EspIr` in `src/bin/creator/bsp/espressif/ir.rs`. Owned by CHIPS-MICROCHIP-01; **does not exist in repo yet**. | This doc. |
| **template set** | The six MiniJinja templates the generator emits per board: `mod.rs.jinja`, `pac.rs.jinja`, `clocks.rs.jinja`, `io_mux.rs.jinja`, `peripherals.rs.jinja`, `board.rs.jinja`. Linker scripts (`memory.x.jinja`, optionally `chip.x.jinja`) are emitted alongside but counted separately. As defined in `src/bin/creator/bsp/espressif/templates/`; used without modification on filename + role. | This doc; mirrors ESP's emission contract. |
| **PMUX function letter** | One of A..H (D5x) or A..N (D21 superset) naming which of the eight alternate functions a SAM pad is multiplexed to. Distinct from the ESP `iomux_fn` integer slot 0..3. The Microchip IR MUST encode this as a single-character string in the YAML, not an integer. See §6 INV-MC2. | SAM D5x/E5x Family Data Sheet §32. |
| **Pad** | A SAM physical pin, identified by `(group, pin)` (e.g. `(0, 23)` = PA23). Distinct from "GPIO" in the ESP sense — a SAM pad does not carry an inherent GPIO number; it carries an alternate-function multiplexer. | SAM D5x/E5x Family Data Sheet §32. |
| **PCHCTRL channel** | Per-peripheral generic-clock channel in GCLK. Each peripheral has a fixed PCHCTRL index (e.g. SERCOM0_CORE is channel 7 on D5x); the chip YAML's `peripherals.<name>.gclk_pchctrl_id:` key records it. Required for SERCOM / TC / TCC / ADC / DAC; not required for AHB-only blocks like NVMCTRL. | SAM D5x/E5x Family Data Sheet §15 Table 15-3. |
| **compile-verify** | The opt-in test pattern that materialises a throwaway cargo project around the generated BSP files and runs `cargo check` against the real upstream PAC on `thumbv7em-none-eabihf` (or `thumbv6m-none-eabi`). Encoded by CHIPS-MICROCHIP-NN as `tests/bsp_microchip_compile.rs` behind a `compile-verify` Cargo feature. As defined in `tests/bsp_esp32c3_compile.rs`; adapted: target triple and PAC crate name are SAM-family-dependent. | This doc; mirrors ESP. |

## 5. Frozen scope and chip inventory

The CHIPS-MICROCHIP family's **chip-family scope** is **Standards
Action** (per CLAUDE.md "Frozen enumerations — registration policy").
Adding a new chip family to in-scope status, demoting an out-of-scope
family to in-scope, or splitting the SAM Cortex-M slice further
requires a §15 amendment to this doc and explicit go-ahead from the
owner.

### In-scope families (CHIPS-MICROCHIP-01 target)

```text
SAM Cortex-M (Atmel-lineage)
    │
    ├─ SAM D5x / E5x  ─ Cortex-M4F @ 120 MHz, FPU, TrustZone-less
    │    PAC family: atsamd5x / atsame5x
    │    Reference parts: ATSAMD51J19A, ATSAMD51J20A, ATSAME54P20A
    │    Toolchain: thumbv7em-none-eabihf
    │    First-board target: TBD in CHIPS-MICROCHIP-01
    │    (recommend: ATSAMD51J19A on a Feather M4 Express form-factor
    │    board, or the official SAM E54 Xplained Pro)
    │
    ├─ SAM D21 / D11   ─ Cortex-M0+ @ 48 MHz, no FPU
    │    PAC family: atsamd21 / atsamd11
    │    Reference parts: ATSAMD21G18A, ATSAMD21J18A
    │    Toolchain: thumbv6m-none-eabi
    │    First-board target: TBD; lower priority than D5x
    │
    └─ SAM L21 / L22   ─ Cortex-M0+ @ 48 MHz, low-power variant
         PAC family: atsaml21 / atsaml22
         Optional in CHIPS-MICROCHIP-01; conditional on D21 landing
         cleanly first.
```

### Out-of-scope families (explicit per §11)

PIC8 (PIC10/12/16/18), PIC24, dsPIC, PIC32 (MIPS-core), megaAVR,
tinyAVR, AVR DA/DB/DD, Microsemi/Microchip FPGAs (PolarFire,
IGLOO2, SmartFusion2), the AT91SAM9 / SAM-A5 Cortex-A line, and the
former Microsemi Cortex-M RISC-V SmartFusion2 / PolarFire SoC parts.
Each is named explicitly so a future contributor doesn't silently
add one without a §15 amendment. See §11.

### Chip inventory YAML format

The chip YAML at `chipdb/rlvgl-chips-microchip/db/chips/<chip>.yaml`
is **Specification Required** (per CLAUDE.md registration policy):
adding a new chip YAML requires a CHIPS-MICROCHIP-NN walkthrough
update but not a §15 concepts amendment. Removing a chip or
renaming its file stem IS Standards Action.

The YAML MUST carry the following top-level keys, mirroring the
ESP chip YAML shape:

| Key | Type | Meaning | Required |
|---|---|---|---|
| `name` | string | Display name, matches the file stem (e.g. `ATSAMD51J19A`). | yes |
| `arch` | string | One of `cortex-m4f`, `cortex-m0+`. Drives target triple selection. | yes |
| `package` | string | Package code (e.g. `TQFP64`, `WLCSP64`). Informative; rendered into `board.rs`. | yes |
| `pac_crate` | string | The crates.io name of the upstream PAC. | yes |
| `pac_version` | string | Minor-version pin (e.g. `"0.13"`). The `compile-verify` test installs this version. | yes |
| `source` | object | `{ datasheet: <DS-number>, revision: <YYYY-MM-DD or rev letter>, errata: <DS-number or null> }`. Cite by Microchip DS-number. | yes |
| `memory` | array | Region list: `{ name, base, size, access }` per the ESP convention. Cortex-M parts always carry at minimum `flash`, `sram`. | yes |
| `clock_tree` | object | See §7 for the SAM-specific shape (GCLK generators + MCLK gates). | yes |
| `peripherals` | map | Peripheral instances keyed by lowercased instance name (e.g. `sercom0`, `tc0`, `tcc0`, `adc0`). Each entry's shape is §8. | yes |
| `io_mux` | array | Per-pad PMUX function table; one entry per `(group, pin)`. Each entry's shape is §9. | yes |
| `linker` | object | `{ region_text, region_data }` naming which `memory.x` regions consume the `riscv-rt`-shaped REGION_TEXT / REGION_DATA aliases. The Microchip equivalent is `cortex-m-rt`'s `RAM` and `FLASH` regions; the alias names in the linker template MUST match `cortex-m-rt`'s `link.x.in`. | yes |

The two stub files do NOT satisfy this shape today. CHIPS-MICROCHIP-01
is the first phase that does.

### Board inventory YAML format

The board YAML at `chipdb/rlvgl-chips-microchip/db/boards/<board>.yaml`
is **Specification Required**. Shape:

| Key | Type | Meaning | Required |
|---|---|---|---|
| `name` | string | Display name, matches the file stem. | yes |
| `chip` | string | The chip YAML's `name`. The build script uses this to populate `BoardInfo::chip`. | yes |
| `flash_mb` | number | On-board flash capacity. Decimal MB; 0.5 is valid (for a 512-KB part). | yes |
| `console` | object | `{ peripheral: <sercom-instance>, baud: <int> }`. The peripheral name MUST appear in the chip YAML's `peripherals:` map with `class: sercom_usart` (or `class: sercom` + `mode: usart`). | optional but recommended |
| `pins` | array | Per-pad assignment: `{ pad: PAxx, signal: <signal-name>, peripheral: <instance-name>, direction: in|out|inout, label: <ident>, pull: up|down|null }`. Pad uses the SAM `PAxx` / `PBxx` / `PCxx` / `PDxx` form, NOT a numeric GPIO. | yes (MAY be empty for a chip-only YAML pair) |
| `i2c_configs` | map | Per-SERCOM SCL frequency override `{ <sercom-name>: { scl_hz: <int> } }`. Mirrors ESP's identically-named map. | optional |
| `spi_configs` | map | Per-SERCOM SPI master timing override `{ <sercom-name>: { clk_hz: <int>, mode: 0..3 } }`. | optional |
| `source` | object | `{ user_guide: <doc-id>, revision: <date>, pinout_sheet: <url-or-null> }`. | yes |

## 6. Frozen invariants

These are properties of the CHIPS-MICROCHIP pipeline that
CHIPS-MICROCHIP-NN execution PRs MUST preserve. Modifying one
requires a §15 amendment. Numbered `INV-MC<n>` to keep them
distinguishable from DCB `INV-D<n>` and other initiatives'
invariants.

- **INV-MC1: Two-step peripheral clock gating.** The
  `clocks.rs` template MUST, for every peripheral that requires
  both an APB bus-clock gate and a GCLK PCHCTRL channel, emit
  writes in the order `MCLK.APBxMASK |= bit` then `GCLK.PCHCTRL[n]
  = (GEN_id | ENABLE)`. APB-only peripherals (NVMCTRL, EIC bus
  side) emit only the MCLK write. GCLK-only peripherals do not
  exist on SAM D-class; if a future chip family violates this, it
  enters scope only via §15 amendment.
- **INV-MC2: PMUX letter encoding.** The chip YAML's `io_mux:`
  entries MUST encode pad alternate-function selectors as
  single-character strings (e.g. `pmux: C`), NOT as integers.
  The `io_mux.rs` template converts these to PMUX field bits at
  emission time (`A=0, B=1, ..., H=7`, and `N=0xf` reserved /
  "no peripheral" on D21-class superset). The two-character
  combined-pad-pair form (`PMUXE` / `PMUXO`) is the SAM register
  encoding; the YAML stays per-pad single-letter and the template
  packs the pair.
- **INV-MC3: PAC instance access style.** Generated code MUST
  use the upstream PAC's uppercase field accessor convention,
  identical to ESP's pattern: `p.SERCOM0.usart_int().ctrla()`,
  `p.PORT.group(0).pmux(11)`, `p.MCLK.apbamask()`, `p.GCLK.pchctrl(7)`.
  Sibling module references inside generated code MUST use
  `super::` (so the output works both as a crate root and as a
  child module of a host crate, per ESP's convention).
- **INV-MC4: chipdb crate public API stability.** The
  `rlvgl-chips-microchip` library API (`vendor()`, `boards()`,
  `find()`, `chip_names()`, `board_names()`, `chip_yaml(name)`,
  `board_yaml(name)`, and the `BoardInfo` struct shape) is
  frozen. New YAML files add slice entries; behaviour PRs MUST
  NOT modify function signatures or `BoardInfo` fields without a
  §15 amendment. Mirrors the ESP / NXP / NRF / RP / Renesas
  public API contracts (the five vendor crates share an identical
  API today).
- **INV-MC5: PAC version pinning.** Each chip YAML carries an
  explicit `pac_version:` minor pin. The generator emits the
  exact `<pac_crate> = "<pac_version>"` line into the
  `compile-verify` test's throwaway Cargo.toml. Upgrading a
  pinned PAC version is Standards Action and rides on a §15
  amendment that names the affected chip YAML file(s) — the
  upstream `atsamd-rs/atsamd` workspace publishes breaking
  changes between minor versions, and a silent bump is the most
  common way a generator silently breaks downstream PRs.
- **INV-MC6: Per-board 6-file template emission.** Every
  successful `bsp from-yaml --vendor microchip --board <board>`
  invocation MUST emit exactly six Rust files (`mod.rs`,
  `pac.rs`, `clocks.rs`, `io_mux.rs`, `peripherals.rs`,
  `board.rs`) into the output directory, plus a `memory.x`
  linker fragment, plus an optional `chip.x` linker fragment if
  the chip YAML's `linker:` block requests it. The snapshot test
  (CHIPS-MICROCHIP-NN `tests/bsp_microchip_render.rs`) enforces
  this by counting files and matching textual snapshots.
- **INV-MC7: Vendor key.** `rlvgl-chips-microchip::vendor()`
  returns the exact string `"microchip"`. The CLI dispatch in
  `rlvgl-creator` matches on this string. Both sides MUST agree;
  renaming the vendor key is Standards Action and would amend
  the cross-crate `chipdb vendor set { esp, nrf, nxp, rp2040,
  renesas, microchip, ... }` enum (CLAUDE.md "Frozen
  enumerations" — same enum that pins the prong set for BBB and
  the build-profile set for DISCO).
- **INV-MC8: No vendored PACs.** CHIPS-MICROCHIP MUST NOT vendor
  a copy of any `atsamd-rs/atsamd`-published PAC. Generated code
  depends on the upstream crate by name + version. The
  `compile-verify` test fetches via crates.io / vendor cache.

## 7. Frozen clock-tree shape

The SAM D-class clock tree is structurally different from
ESP's `system_gates` flat table. The chip YAML's `clock_tree:`
block MUST carry:

```yaml
clock_tree:
  xosc_hz: 12000000       # External crystal (if applicable); null otherwise.
  dfll_target_hz: 48000000  # DFLL48M frequency (D21 / L21) or null on D5x.
  dpll_target_hz: 120000000 # FDPLL target (D5x / E5x); null otherwise.
  cpu_hz: 120000000
  apba_hz: 60000000       # APB-A divider output (or = cpu_hz if no divider)
  apbb_hz: 60000000
  apbc_hz: 60000000       # D5x carries APB-C; D21 omits and uses null.
  apbd_hz: 60000000       # D5x carries APB-D; D21 omits.
  gclk_generators:
    - { id: 0, source: dpll0, div: 1 }    # generator 0 -> CPU
    - { id: 1, source: xosc32k, div: 1 }  # generator 1 -> RTC
    - { id: 2, source: dfll48m, div: 1 }  # generator 2 -> USB
  mclk_gates:
    sercom0: { reg: apbamask, field: sercom0_ }
    sercom1: { reg: apbamask, field: sercom1_ }
    # ... per peripheral ...
  pchctrl_channels:
    sercom0_core: { id: 7,  generator: 0 }
    sercom0_slow: { id: 3,  generator: 2 }
    # ... per generic-clock channel ...
```

The exact field names + nesting are **Standards Action** — the
`clocks.rs.jinja` template reads these by path, so a rename ripples
through the template set. Adding a new top-level key (e.g.
`backup_clock:` for the SAM L line) requires a §15 amendment.

Concrete bit positions, register addresses, and `apbamask` field
names: **TBD: needs Microchip SAM D5x/E5x Family Data Sheet
(DS60001507) §15 (GCLK) and §16 (MCLK) cite for each `gclk_pchctrl_id`
and each `mclk_gates` field name.** CHIPS-MICROCHIP-01 lands the
first chip YAML with these populated.

## 8. Frozen peripheral-instance shape

Per-peripheral entries in the chip YAML's `peripherals:` map MUST
carry:

| Key | Type | Meaning |
|---|---|---|
| `class` | string | One of `sercom`, `tc`, `tcc`, `adc`, `dac`, `usb`, `eic`, `nvmctrl`, `dmac`, `wdt`, `rtc`, `pukcc`. Drives the `peripherals.rs.jinja` per-class init branch. |
| `instance` | string | The PAC instance name (`sercom0`, `tc4`, etc.). Lowercase. The template uppercases at the access boundary per INV-MC3. |
| `base` | int | MMIO base address. Informative; the generator does not emit raw addresses (PAC handles it) but the snapshot tests include this for human review. |
| `irq` | int or null | NVIC interrupt vector number. Null for peripherals that do not request an interrupt. |
| `mclk_field` | string | The `apbamask` / `apbbmask` / `apbcmask` / `apbdmask` field name to write `1` to in `clocks.rs`. Resolved against `clock_tree.mclk_gates[instance]`. |
| `gclk_pchctrl_id` | int or null | The PCHCTRL channel index. Null for AHB-only peripherals. |
| `mode` | string or null | For `sercom` only: one of `usart`, `i2c_master`, `i2c_slave`, `spi_master`, `spi_slave`. Drives which init branch the template emits. Null if the SERCOM is not assigned a role by the board. |
| `signals` | array | Per-signal pad-routing entries: `{ role, direction, pad: PAxx, pmux: <letter> }`. The `role` field is class-specific (`tx`/`rx`/`cts`/`rts` for USART; `sda`/`scl` for I²C; `sck`/`mosi`/`miso`/`cs` for SPI). |

The **Specification Required** policy applies to adding new
`class:` values (mirrors ESP's `class:` set: adding `class: spi_quad`
or `class: can` requires a per-PR walkthrough update, no §15
amendment); demoting an existing `class:` is Standards Action.

## 9. Frozen pad-mux table shape

The chip YAML's `io_mux:` array MUST have one entry per addressable
pad on the chip's package, in `(group, pin)` order:

```yaml
io_mux:
  - { pad: PA00, group: 0, pin: 0,  fn_a: null,        fn_b: null,        fn_c: SERCOM1_PAD0, fn_d: TCC2_WO0,   fn_e: null, fn_f: null,  fn_g: null,         fn_h: null,        analog: AIN0 }
  - { pad: PA01, group: 0, pin: 1,  fn_a: null,        fn_b: null,        fn_c: SERCOM1_PAD1, fn_d: TCC2_WO1,   fn_e: null, fn_f: null,  fn_g: null,         fn_h: null,        analog: AIN1 }
  # ... per pad ...
```

Function-letter columns are nullable: not every pad supports every
alternate function. The `io_mux.rs.jinja` template reads each
board pin's `pmux:` letter and looks up the matching `fn_<letter>`
column on the chip YAML, then emits the PMUX write. A mismatch
(board YAML names `pmux: D` but chip YAML's `fn_d:` is null for
that pad) is a generator-level error and MUST fail
CHIPS-MICROCHIP-01's snapshot test rather than emit broken code.

Pad count per package: **TBD: needs Microchip SAM D5x J-pkg (64-pin
TQFP) and G-pkg (48-pin TQFP) Family Data Sheet §6 (Pinout) cites.**
The chip YAML's `io_mux:` array length MUST equal the count from
the datasheet pinout chapter; CHIPS-MICROCHIP-01's load step
asserts this.

## 11. Non-goals

Explicitly out of scope for the CHIPS-MICROCHIP family until a
future §15 amendment names the first user and the spec lineage to
ratify against. Each item is a **Standards Action** addition: a
future spec doc would have to amend §5's chip-family scope before a
behaviour PR could land. Surfaced here so a future contributor does
not silently add one.

1. **PIC8 family** (PIC10F / PIC12F / PIC16F / PIC18F). 8-bit
   Harvard architecture; no Rust support today; would require a
   different toolchain (the `mplabxc8` C compiler or a community
   AVR-style Rust fork). No `compile-verify` story.
2. **PIC24 / dsPIC** (16-bit). Same Rust-availability problem;
   embedded-rust support is nascent at best.
3. **PIC32 (MIPS-core)** (PIC32MX / PIC32MZ). 32-bit MIPS; Rust
   support exists upstream (`mipsel-unknown-linux-musl`-style
   targets) but no published PAC ecosystem. **Out until a
   community svd2rust pipeline lands.**
4. **megaAVR / tinyAVR / AVR DA / DB / DD / EA** (8-bit Atmel-AVR
   lineage). Rust support exists via the `avr-hal` ecosystem and a
   community `avr-unknown-gnu-atmega328` target, but the PAC
   convention is different (it's `embedded-hal` traits, not
   svd2rust). Adding AVR would require a separate vendor crate
   (`rlvgl-chips-microchip-avr`) and an `--vendor microchip-avr`
   CLI key. **Standards Action; deferred to a separate initiative
   family if pursued.**
5. **Microchip / Microsemi FPGAs** (PolarFire, IGLOO2, SmartFusion2,
   ProASIC3). Out of vendor scope entirely — these are FPGA
   fabrics, not MCUs.
6. **SmartFusion2 Cortex-M3 / PolarFire SoC RISC-V hard cores**.
   Closer to in-scope (they ARE MCU-class targets with PAC
   feasibility), but the toolchain story diverges from the
   atsamd-rs ecosystem. **Standards Action; would need its own
   sub-letter spec.**
7. **AT91SAM9 / SAMA5 Cortex-A line** (e.g. SAMA5D27). These are
   Linux-class application processors; bringup is U-Boot + Linux
   rather than a `cortex-m-rt` reset handler. **Out — does not
   match the chipdb / BSP-emit shape.**
8. **AT32UC3 (AVR32 line)**. Pre-Microchip-acquisition Atmel AVR32
   parts; no Rust target. Out.
9. **SAM4S / SAM4E / SAM4N / SAM4L (older Cortex-M3 / M4 line,
   pre-D5x)**. These ARE Atmel-lineage SAM Cortex-M parts and
   could fit the §5 frame, but the upstream PAC ecosystem
   (`atsam-rs/atsam`) is less actively maintained than the
   D-class line and lacks `compile-verify`-quality coverage.
   **Standards Action; expected as a CHIPS-MICROCHIP-NN follow-on
   once D5x and D21 ship.**
10. **MPLAB Harmony / MCC / Atmel START generated code parsing**.
    The C1 Microchip MCC parser sketched in
    `docs/bsp/CHIP-SUPPORT.md` Epic C3 is **out of scope for
    CHIPS-MICROCHIP-NN**. CHIPS-MICROCHIP consumes hand-authored
    YAML (the chipdb pattern) and does NOT scrape upstream MCC
    output. A future Harmony / MCC ingest pipeline would file as a
    separate initiative under `docs/bsp/` and cite this doc for
    the IR target shape.
11. **EIC (External Interrupt Controller) init code**. The chip
    YAML's `peripherals:` map MAY include EIC instances, but the
    `peripherals.rs.jinja` template MUST NOT emit interrupt-line
    routing in CHIPS-MICROCHIP-01. Adding EIC init is
    **Specification Required**: a CHIPS-MICROCHIP-NN walkthrough
    update suffices.
12. **DSU (Device Service Unit), TCC waveform output beyond
    register-block reset, full ADC / DAC calibration loading
    from NVM user-row fuses**. All deferred to a follow-up; the
    pipeline's job is bring-up, not full peripheral configuration.
    Standards Action for any of these to enter scope.
13. **Hardware bench validation**. The CHIPS-MICROCHIP-NN family
    targets *generator correctness* (snapshot + compile-verify
    test parity). Burning the generated BSP to a real Xplained
    Pro / Feather M4 and observing UART console output is a MAY
    conformance level, not a MUST. Mirrors the ESP family — the
    `beetle-esp32c3` `--features bsp_pac` LED-blink demo proves
    the pipeline boots, but the initiative's MUST gates stop at
    `compile-verify`.

## 12. Acceptance checklist

A future CHIPS-MICROCHIP-NN sub-letter analysis is "Ratified" only
when it can cite the gates that have been satisfied. The
initiative-level (cross-phase) gates:

**(a)** The chipdb crate carries at least one **non-stub** chip
YAML satisfying §5 (all required keys present, `memory:` /
`clock_tree:` / `peripherals:` / `io_mux:` populated against a cited
Microchip datasheet) and at least one **non-stub** board YAML
(`pins:` non-empty for the chip's package, `console:` set, cited
user-guide source). The recommended first chip is `ATSAMD51J19A`;
the recommended first board is the Adafruit Feather M4 Express or
the Microchip SAM D51 Curiosity Nano (both ship readily, both have
public pinout sheets). MUST.

**(b)** A `MicrochipIr` + load + render pipeline exists under
`src/bin/creator/bsp/microchip/` with the four files (`ir.rs`,
`load.rs`, `render.rs`, `mod.rs`) and the six-template set under
`templates/` per INV-MC6. The CLI's `bsp from-yaml --vendor
microchip` route dispatches into it. The legacy
`src/bin/creator/bsp/microchip.rs` shim is deleted. MUST.

**(c)** A snapshot test
`tests/bsp_microchip_render.rs` exists under `--features creator,regression`
and matches `tests/bsp_esp32c3_render.rs` in shape: per-board fixture
generation, file-count assertion, byte-equivalent textual match
against committed snapshot output. MUST.

**(d)** A `compile-verify` test
`tests/bsp_microchip_compile.rs` exists under
`--features compile-verify` and materialises a throwaway cargo
project around the generated files. The throwaway project depends
on the chip YAML's pinned `pac_crate` + `pac_version` and runs
`cargo check --target thumbv7em-none-eabihf` (or `thumbv6m-none-eabi`
for D21-class chips). Test-thread serialisation
(`-- --test-threads=1`) matches the ESP-side convention. SHOULD.

**(e)** The Pre-Publish Validation phase 4.6 (or a new phase 4.8
specifically for Microchip) in `CLAUDE.md` lists a matching
`cargo test -p rlvgl-chips-microchip` + `cargo test -p rlvgl --test
bsp_microchip_render --features creator,regression` + (opt-in)
`cargo test -p rlvgl --test bsp_microchip_compile --features
compile-verify -- --test-threads=1` triplet. MUST after CHIPS-MICROCHIP-04
lands; SHOULD during the staging phases.

**(f)** Hardware-bring-up parity with the `beetle-esp32c3`
`--features bsp_pac` shape: an `examples/<microchip-board>/`
crate with two feature flags (`mchip_hal` for an established
high-level path, e.g. `atsamd-hal`; `bsp_pac` for the
generated-BSP path) under `examples/`. The `bsp_pac` build proves
the pipeline boots; the `mchip_hal` build proves the example app
works with idiomatic code. MAY (deferred — see §11 #13). The
ESP family treats this as MAY too; the conformance level for
CHIPS-MICROCHIP-NN tracks ESP.

**(g)** This concepts doc has been ratified (§15 dated entry
moves from `DRAFT — awaiting ratification` to `Ratified
<date>`) **before** any behaviour PR claims a `CHIPS-MICROCHIP-NN`
prefix. MUST. Per the CLAUDE.md "Execution discipline" clause:
"Touching a frozen enum value or an invariant requires a
change-log amendment first, in a separate PR."

**(h)** When the CHIPS-MICROCHIP family reaches natural
completion (D5x and D21 chip families both have at least one
chip + one board shipping, snapshot + compile-verify gates green,
the `--vendor microchip` CLI dispatch stable), an initiative
retrospective lands at `chipdb/rlvgl-chips-microchip/docs/CHIPS-MICROCHIP-RETROSPECTIVE.md`
following the §1–§7 shape from CLAUDE.md "Initiative
retrospective". MUST.

- **2026-05-13 — MICROCHIP-02 amendment.**
  `src/bin/creator/bsp/microchip/templates/` `clocks.rs.jinja`,
  `io_mux.rs.jinja`, and `peripherals.rs.jinja` now emit
  field-direct register access (`p.MCLK.apbamask`,
  `p.GCLK.pchctrl[N]`, `p.GCLK.pchctrl[N].read().chen()`,
  `p.PORT.group0.pmux[H]`, `p.PORT.group1.pincfg[P]`,

  `.syncbusy`) instead of the modern method-style access shape

  `p.PORT.group(N).pmux(H)`, etc.). This matches the pinned
  `atsamd51j19a 0.7.1` PAC crate's pre-method-accessor svd2rust
  era output: `MCLK.APBAMASK` is a struct field of type
  `APBAMASK`, `GCLK.pchctrl` is `[PCHCTRL; 48]`, `PORT.group0`

  `GROUP` the `pmux` / `pincfg` are fixed arrays. The
  mode-union accessors on `SERCOM*` (`usart_int()`, `i2cm()`,
  `spim()`) and the union-variant `baud()` method on
  `USART_INT` remain methods on this PAC era; only the
  per-register field handles (`ctrla`, `ctrlb`, `syncbusy`)
  change to field access. The `gen` writer field on
  `GCLK.PCHCTRL` is also emitted as `w.gen()` (not `w.gen_()`)
  per the PAC's actual writer name on this era. The opt-in
  compile-verify gate (`bsp_microchip_compile` under
  `--features compile-verify`, §12 (d)) now passes end-to-end
  against `atsamd51j19a 0.7` on `thumbv7em-none-eabihf`.
