# v0.2.7 MPY subscription snapshot owner decision

Recorded 2026-10-06. This informative disposition records owner decision 3:
**accept reuse of the existing neutral `SubscriptionInfo` metadata and atomic
full-page preparation before cursor advance.** The owner subsequently accepted
one owning-Stage revision increment for successful subscription addition or
actual removal, unchanged revisions on failed/idempotent operations, and
isolation between Stages. It follows the
[next-slice prerequisite packet](v0.2.7-mpy-next-slice.md). These principles and
the revision rule are now narrowly normative in MPY-04 §15 0.15.2 and MPY-05
§15 0.2.3; exact bounds/fields/API below remain proposals. No Rust, coverage
status, handoff acknowledgment or PCDN was changed.

## Accepted scope and existing authority

[MPY-04 §8.2](../concepts/MPY-04-STAGE-DIRECTIONS-INTROSPECTION.md#82-snapshot-shape)
requires active subscription metadata without callable pointers, deterministic
actor traversal and pages consistent at one Stage Revision.
[MPY-05 §6](../concepts/MPY-05-CUES-SAFE-SCHEDULING.md#6-frozen-decisions--subscription-lifecycle)
owns token identity, validation, idempotent removal and teardown. The existing
[`SubscriptionInfo`](../../core/src/subscription.rs) is an allocation-free
neutral value with integer callback identity; it retains no VM callable.

Atomic full-page preparation means every actor record and retained subscription
row must exist before position, sequence, or successful end-of-cursor release
commits. It does **not** require exactly one allocation. Reservations and all
fallible reads may precede one cursor commit boundary; allocation failure must
leave the same page available for retry. Explicit staleness and teardown retain
their required cursor-release behavior.

The owner has selected subscription/Stage revision coupling as recorded below.
Exact budget/API representation and the field projection detailed below remain
unselected. Acceptance of the principles does not select those details.

## Proposed minimal record and bounds

Use the existing `SubscriptionInfo` directly as each row; introduce no second
subscription metadata schema. Proposed actor-record additions are
`subscriptions: Vec<SubscriptionInfo>`, `total_subscriptions: usize` and
`subscriptions_truncated: bool`. These names and bounds are review proposals.

| Existing field | Proposed projection |
| --- | --- |
| `subscription_id` | Exact active runtime token; no tombstone rows. |
| `stage_id` | Owning Stage, equal to the snapshot's Stage. |
| `actor_identity` | Exact ObjectId and TypeId, matching the actor record. |
| `callback_id` | Existing opaque integer CallbackId, without callable lookup, pointer, name or adapter data. |
| `event_id` | Existing descriptor event identifier. |
| `phase` | Existing native propagation phase. |
| `filter` | Existing validated neutral filter. |
| `propagation` | Existing predeclared policy. |
| `registration_order` | Existing endpoint-wide order, used to preserve row order. |

Retain MPY-04 root-order/pre-order actor traversal. Within each record, filter
the registry's active metadata by exact Stage and actor identity, preserving
registration order. Apply a caller-supplied `max_subscriptions_per_record` to
the leading rows; count all matching active rows before bounding. A strict
prefix sets `subscriptions_truncated` and the aggregate record `truncated` bit.
A zero subscription budget is valid and reports truthful total/truncation;
`max_records == 0` remains invalid. Keep text and style limits independent.
All row storage is bounded by this limit and the existing registry capacity.

The subscription-bearing operation needs coordinated access to both the Stage
and the registry, naturally at the existing
[`Endpoint`](../../core/src/endpoint.rs) owner. Its exact method signature is
not selected. Preserve existing Stage-only snapshot entry points. They cannot
truthfully report endpoint subscription totals without registry access: do not
silently decorate their already-returned pages or present an unobserved count as
zero. A compatibility wrapper with a zero subscription budget must delegate
through a registry-aware operation if it promises complete metadata counts.
No wire format, MicroPython projection or additional negotiated capability is
proposed here.

## Accepted revision rule

The existing [`StageRegistry` cursor](../../core/src/actor.rs) freezes only
Stage Revision. `SubscriptionRegistry::subscribe()` reads an immutable Stage;
successful subscribe/remove advances a separate private registry revision.
Consequently, the current Stage token alone cannot detect changed subscriptions.

**Owner accepted 2026-10-06:** make a successful visible subscription
addition or actual removal advance the owning Stage Revision once, atomically
with the registry mutation. This preserves MPY-04's existing starting/current
Stage Revision and `SnapshotStale` contract. Keep the registry's own revision
for its existing prepared-work guards; the two counters need not become equal.

The amended MPY-04/05 requirements and existing atomic/lifecycle rules imply:

- Preflight both revisions, identities and capacity before publishing either
  mutation; revision exhaustion must leave both owners unchanged.
- A failed subscription request, stale removal or matching `AlreadyRemoved`
  outcome changes neither revision. This matches the existing active-record
  change boundary; it does not alter accepted Batch no-op revision semantics.
- Changing another Stage's subscription must not stale this Stage's cursor.
- Actor deletion or Stage teardown that already publishes a Stage mutation
  must not gain an additional Stage increment for its subscription cleanup.
  Preserve child-first removal and exact-once teardown notices.
- Stage teardown and Endpoint Epoch replacement release/invalidate the cursor
  as required; retain existing identity and lifecycle guarantees.

The unselected alternative was to freeze both Stage and subscription revisions in a coordinated
cursor. The current registry revision is endpoint-wide, so using it directly
would also stale a cursor after another Stage's subscription change. Avoiding
that requires a per-Stage revision design or explicit acceptance of conservative
cross-Stage invalidation. The existing Stage-only `SnapshotError::Stale` cannot
express a registry-only change accurately without an owning error/API decision.
This is why the alternative is not a drop-in implementation detail.

## Page preparation and proof after disposition

Prepare the traversal slice, actor fields, subscription counts and retained
prefixes against the selected revision guard. Complete all fallible work before
the single cursor commit, including the last page's release. On allocation
failure retain position and sequence; on successful zero-budget truncation
advance them. Do not call the current committing `snapshot_read` and decorate
its returned page afterward. The internal prepare/commit shape remains an
implementation choice once the source handoff and contract are approved.

New evidence must cover interleaved two-actor/two-Stage registrations, every
projected field, absence of tombstones, zero/partial/full bounds, addition/removal
between pages, failed/idempotent changes, other-Stage isolation, revision
exhaustion, allocation failure during subscription preparation and same-page
retry, final-page failure, child-first teardown, epoch replacement and unchanged
property/style ordering. Run affected existing conformance alongside the new
snapshot suite; do not treat old tests as proof of this unimplemented behavior.
