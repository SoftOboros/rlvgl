# RLVGL v0.2.7 family work plan

The release target is `v0.2.7`, with `rlvgl-core 0.2.7` and selective versions
for the other packages. Bring each admitted deliverable to a documented resting
point: demonstrated acceptance, an explicit remaining evidence gate, or an
owner-controlled deferral. A source checkpoint does not establish package,
board, interpreter, or family conformance.

This is an informative execution plan dated October 5, 2026. The owning SBC
phase and its dated ratification remain authoritative. This plan neither
ratifies a phase nor resolves a PCDN. Three subagents reviewed MPY, CPY, and
Wayland/embedded deliverables; no implementation or new tests were performed
as part of this planning pass.

The owner subsequently **accepted this plan** and directed parallel execution.
The [execution receipt](v0.2.7-family-execution.md) records completed slices
and remaining stop points; acceptance of this plan does not ratify a draft
family phase or amendment.

## Authority and stopping rules

Before executing an assignment, read the owning phase, its dependencies,
acceptance checklist, change log, and family errata. Check the actual phase
record rather than relying on an older overview page. Follow
[current SBC adoption](../spec-index/SBC-COMPATIBILITY.md) and
[the operational instructions](../../CLAUDE.md).

- Execute only specified work and tests whose phase authority and dependencies
  are satisfied. A resolved PCDN does not by itself ratify its phase.
- Stop dependent work at an unresolved PCDN, missing ratification, normative
  discrepancy, missing shared-path handoff, or required external evidence.
  Continue unrelated assignments that remain eligible.
- At a stop, return the exact phase/PCDN or errata handle, source citation,
  completed evidence, decision needed, affected paths, and proposed next step.
  Prepare options without choosing policy or changing acceptance criteria.
- Preserve historical evidence. Add a new receipt for current verification;
  do not rewrite measurement commits, hashes, qualification, or old closeouts.
- Close a task at its stated evidence boundary. Do not grow a failed test into
  a cross-family repair, change a baseline, or treat a host check as board proof.

## Deliverable boundaries and following work

[MPY-05](../concepts/MPY-05-CUES-SAFE-SCHEDULING.md) are ratified. Their status
prose understates existing native integration. Start with evidence, not a new
implementation of code already present.

Use the existing suites under `core/tests/mpy_*.rs` and
`widgets/tests/mpy_*.rs`, selecting the acceptance rows under review. Validate
the coverage schema with `tests/test_mpy_coverage_matrix.py`; have the
coordinator run `make spec-index` and `make spec-test spec-index-check`.

After reconciliation, snapshot subscription metadata is a possible bounded
MPY-04 implementation slice. It needs an exact path handoff and confirmation

existing proof are available, while new binding/conformance behavior remains

with actual MicroPython API, full cross-driver corpus, board transport and
release/performance claims individually accounted for.

### CPY native service and Python delivery

[CPY-00 through CPY-02](../cpython/README.md) are ratified; CPY-03 through
CPY-09 remain Draft. The implemented native-only service and host diagnostics
are the existing resting point. There is no implemented PyO3 adapter, Python
Frame Lease or Python distribution to qualify.

The first slice uses existing `scripts/cpy_evidence.py` checks and firewall
plus their checker negative controls; use Python 3.11 or newer. New measurements
need clean committed source and a new evidence name. Physical BBB qualification
of the representative native workload is the next CPY-03 evidence gate, followed
by owner ratification; it does not require a Python binding or physical display.

Subsequent planning can map CPY-04 methods/callbacks, CPY-05 frame lifetime
vectors, CPY-06 embedded-Linux capture, CPY-07 OS/asyncio proofs, and CPY-08/09
artifact claims to their owning acceptance rows. Stop at `PCDN-CPY-05-002`,

decisions where applicable. Repository/core 0.2.7 does not select the Python
artifact version (`PCDN-CPY-09-004`).

### Wayland presentation and input

## Packaging and final integration

The CRATES-CI correction packet must preserve progressive dependency order,
exact packaged source inventory, metadata checks, existing-version drift
checks, clean-source refusal, and consumers that use only extracted packages.
Prove the missing-predecessor negative control, the staged-predecessor positive
control, absence of live-workspace paths, and lockfile restoration. Update the
documented core/bridge mechanism through the owning SBC amendment workflow;
do not turn a required decision into an implementation assumption.

After the mechanism is effective, run complete Gate P staging and all three
packaged consumers: library, creator CLI and user simulator. The 13-package
publish selection is not permission to omit unchanged packages from the full
gate or skip content-drift checks. Re-evaluate selective versions if family
work adds changed package content.

The first-publish instructions currently name a 0.1.0 bootstrap for the earlier
bridge. Reconcile that example with the device crates' allocated 0.2.5 versions
before preparing their operator publication sequence; do not silently change
versions or configure credentials.

At integration, review each worker's spec references, diff, test receipt and
stops. Run applicable pre-publish checks once on the assembled candidate;
focused checks do not replace the full release gates. Publish/fetch-verify the
exact nested Ratatui source before the final RLVGL gitlink, then review the
chosen parent branch and update only its intended pin. The parent branch must
be selected explicitly; the dirty recovery checkout is not an automatic
publication target.

The release resting point requires a reviewed claims matrix, clean source
checkpoint, exact nested refs and parent pin, Gate P before tagging, per-crate
publication prerequisites, and Gate R after publication. Open PCDNs, physical
proof and interpreter releases remain visible with their owning family.
