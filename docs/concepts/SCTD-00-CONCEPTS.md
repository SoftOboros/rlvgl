# SCTD-00 - SCXML Tutorial Demo Concepts

**Status:** Ratified 2026-06-19. Normative for the SCTD initiative
(SCXML Tutorial Demo for v0.2.5).

Requesting ticket: start the `v0.2.5` branch and add another
state-chart demo app based on the Alex Z SCXML tutorial examples
vendored as the `tutorial` submodule of `scjson`. The initial demo set
should include examples such as Dining Philosophers and the media-player
style Skoda Bolero infotainment machine, selectable through right-edge
icons in the same screen position as the disco demo. Rust packages for
the state charts will be generated by iState through the Softoboros MCP
codegen tools. Machine-specific visual assets should come from the
tutorial examples where available, with Lucide used only as a
supplemental source for missing selector or utility icons. The app must
remain buildable on all currently supported rlvgl targets.

## 0. Authority Policy

This document is the normative source for SCTD vocabulary, invariants,
and phase acceptance. If a future SCTD phase changes a frozen decision in
§5-§9, this document's §15 MUST be amended first.

## 1. Purpose

Add a second state-chart demo application that proves rlvgl can host
non-trivial SCXML tutorial machines as user-visible demos, not just as
offline generated Rust packages. The app should let a user choose tutorial
examples from the right-edge icon strip and observe each selected state
machine through a compact rlvgl UI.

## 2. Problem Statement

rlvgl and Softoboros already carry the plumbing for external SCXML
state-machine generation:

- `docs/app-schema/04-state-machine-boundary.md` defines the
  vendored-crate offline model.
- the Softoboros MCP surface exposes `istate_upload_xml` plus
  `istate_codegen_create/status/download`; `rust` is an explicit target
  language.
- the iState backend renders Rust code from
  `backend/templates/codegen/rust/` and bundles verification vectors.
- current iState-generated bundles still emit a compatibility
  `.mcp-statechart-manifest.json`; SCTD treats that file as a legacy
  manifest shape, not as the generator authority.
- `examples/stm32h747i-disco/disco-demo-states/` is a generated state
  machine crate with vectors.

That proves the generator boundary, but it does not prove that multiple
external tutorial machines can be presented as an interactive app across
the supported rlvgl target wrappers. The Alex Z SCXML tutorial examples
are already vendored under `vendor/scjson/tutorial/Examples/`, including:

- `StateCharts/DiningPhilosphersProblem/machine_dining_philosphers.scxml`
- `StateCharts/DiningPhilosphersProblem/machine_dining_philosphers.flat.scxml`
- `Qt/DiningPhilosophers/Src/machine_dining_philosphers.flat.scxml`
- `Qt/SkodaBoleroInfotainment/Model/bolero.scxml`
- `Qt/StopWatch/StopWatch.scxml`
- `Qt/Morse/Src/*.scxml`

SCTD exists to freeze how those examples enter rlvgl before code lands:
which examples are in scope, how iState-generated Rust packages are
named and verified, how the right-edge icon selector behaves, and how
the app remains portable.

## 3. Glossary

| Term | Meaning | Owner |
|---|---|---|
| **Tutorial Source** | An upstream SCXML file under `vendor/scjson/tutorial/Examples/`. SCTD treats this as read-only input. | scjson tutorial |
| **Tutorial Asset** | An upstream image, SVG, QML, UI, or resource-manifest asset shipped beside a Tutorial Source. SCTD treats this as read-only input and transcodes copies for runtime use. | scjson tutorial |
| **Tutorial Machine** | A Rust package generated by iState MCP from one Tutorial Source and accompanied by a self-manifest plus verification vectors. | SCTD |
| **Tutorial Demo App** | The rlvgl app crate that owns the right-edge selector, per-machine panels, and event controls. | SCTD |
| **Machine Selector** | The right-edge icon strip used to choose a Tutorial Machine. It is position-compatible with the disco demo's main icon strip. | SCTD |
| **Machine Panel** | The visible UI region for the selected Tutorial Machine: current states, queued or enabled events, and domain-specific controls. | SCTD |
| **Target Wrapper** | A host or board-specific binary that mounts the Tutorial Demo App and supplies display, input, ticks, storage policy, and optional serial/playit hooks. | repo |

## 5. Frozen Decisions - Example Admission

1. **Initial SCTD admission set.** SCTD-01 MUST admit these tutorial
   machines first:
   - Dining Philosophers, using the flat SCXML form when the generator
     cannot resolve includes portably.
   - Skoda Bolero infotainment, represented in the UI as the media
     player example.
2. **Stretch examples.** StopWatch and Morse MAY be added after the two
   required examples build and have verification vectors. They MUST NOT
   block SCTD-01 acceptance.
3. **Source immutability.** Tutorial Source files under `vendor/scjson`
   MUST NOT be edited. If a source requires normalization, the normalized
   form lives under the SCTD generated/input area with provenance back to
   the original path.
4. **Generated output location.** Generated Tutorial Machine packages MUST
   live outside `_generated/` directories but MUST carry clear generation
   provenance and a self-manifest. Until the app-schema manifest is
   amended, the compatibility self-manifest MAY remain
   `.mcp-statechart-manifest.json` even though iState MCP is the
   generator authority.
5. **Verification vectors required.** Each admitted Tutorial Machine
   MUST carry at least one deterministic vector test before it can appear
   in the app selector.
6. **Interactive Dining Philosophers (SCTD-02 amendment, 2026-06-20).**
   An **Interactive Dining Philosophers** machine is admitted as a
   distinct Tutorial Machine — a normalized variant with provenance to the
   SCTD-01 faithful DP (per item 3), adding host-injected lifecycle events
   (`PHILOSOPHER_ARRIVE` / `PHILOSOPHER_DEPART` / `DEADLOCK_BREAK` /
   `SIMULATION_RESET`). The faithful DP machine (item 1) is unchanged. The
   interactive variant's contract is owned by
   [`SCTD-02-FIREBEETLE-P4-INTERACTIVE.md`](SCTD-02-FIREBEETLE-P4-INTERACTIVE.md)
   §5; its lifecycle event enum carries the **Specification Required**
   registration policy defined there.

## 6. Frozen Decisions - App Surface

1. **App crate shape.** The Tutorial Demo App MUST be a target-neutral
   Rust crate under `examples/apps/`. It may depend on generated Tutorial
   Machine packages by path, but it MUST NOT contain board-specific
   initialization, PAC access, OS calls, file I/O requirements, or wall
   clock assumptions.
2. **Selector position.** The Machine Selector MUST use the same
   right-edge screen position as the disco demo's icon strip. Exact icon
   artwork may differ.
3. **Selector contents.** The required initial selector entries are:
   Dining Philosophers and Media Player. A third Info/About entry MAY be
   present if needed for discoverability or diagnostics.
4. **Tutorial assets first.** Machine-specific visuals MUST prefer
   Tutorial Assets when the tutorial provides a suitable image or UI
   resource. Known initial candidates include Dining Philosophers SVGs
   under `Qt/DiningPhilosophers/Images/` and Skoda Bolero media/control
   PNGs under `Qt/SkodaBoleroInfotainment/Qml/Images/`.
5. **Runtime asset copies.** SCTD MUST NOT render directly from
   `vendor/scjson/tutorial` at runtime. Assets used by the app are copied
   or transcoded into the app's asset tree with provenance back to the
   tutorial source path.
6. **Selector icons.** Selector icons SHOULD use Tutorial Assets when a
   clear glyph exists, such as Skoda media images for Media Player. Lucide
   MAY fill gaps, for example if Dining Philosophers needs a simplified
   strip glyph that is not practical to derive from the tutorial SVGs.
7. **Asset transforms.** SVG-to-raster/RLE, PNG-to-RLE, cropping, palette
   reduction, and scaling are allowed if deterministic and documented in
   the app asset README or generation script. Transforming an asset MUST
   NOT mutate the upstream tutorial file.
8. **Machine Panel.** Each selected machine MUST expose current active
   state names and available demo events without requiring serial or
   debugger access. Machine-specific visualization is allowed but must
   remain secondary to state observability.
9. **Event dispatch.** User-facing controls MUST dispatch named SCXML
   events through a small adapter layer. UI code MUST NOT reach into
   generated internals beyond the generated public API and self-manifest
   state/event vocabulary.

## 7. Frozen Decisions - Target Portability

1. **No target-only app logic.** Target wrappers may mount the app and
   translate input, but all tutorial-machine selection and event routing
   lives in the Tutorial Demo App crate.
2. **Supported target meaning.** For SCTD-01, "all currently supported
   targets" means every target wrapper that can already mount an rlvgl
   app payload from this workspace without adding new hardware bring-up:
   host simulator, disco simulator, STM32H747I-DISCO bare-metal,
   STM32H747I-DISCO FreeRTOS, and UEFI disco where the existing build
   profile supports app payloads.
   **SCTD-02 amendment (2026-06-20):** the supported-target set additionally
   includes **FireBeetle 2 ESP32-P4 + DFR0550-V2, via
   `examples/beetle-esp32p4-idf` (ESP-IDF)**. That target rides an
   already-brought-up hardware path (the BEETLE family + C host own
   DSI/DPI/PSRAM/cache/touch/double-buffer); SCTD owns only the Rust pixel
   payload + logical-tick cadence. Contract owned by
   [`SCTD-02-FIREBEETLE-P4-INTERACTIVE.md`](SCTD-02-FIREBEETLE-P4-INTERACTIVE.md)
   §7. The raw-PAC `examples/beetle-esp32p4` port remains out of scope.
3. **Build gate.** SCTD implementation MUST add build checks for the
   Tutorial Demo App on host plus at least the same embedded target
   triples exercised by the existing disco demo gates. Hardware flashing
   is not required to ratify the concept, but a hardware smoke gate is
   RECOMMENDED before publishing v0.2.5.
4. **Resource budget.** The app MUST compile in `no_std + alloc` mode
   for embedded targets. Generated machines that require dynamic maps,
   heap-heavy data models, or unsupported ECMAScript hooks MUST be
   adapted behind the generated-machine boundary or deferred.

## 8. Frozen Decisions - iState MCP Boundary

1. **Generator authority.** SCTD MUST generate Tutorial Machine Rust
   packages through iState over MCP. The expected flow is upload or
   create the SCXML document with iState, call `istate_codegen_create`
   with `target_langs=["rust"]`, poll `istate_codegen_status`, and fetch
   the Rust artifact with `istate_codegen_download`.
2. **Self-manifest required.** Every Tutorial Machine package MUST carry
   a self-manifest with a state set and file inventory. The current
   compatibility filename is `.mcp-statechart-manifest.json`; changing
   that filename or tool-name field is a separate app-schema amendment.
3. **No runtime SCXML parsing.** Target binaries MUST NOT parse SCXML at
   runtime. SCXML is build-time input only.
4. **External behavior caveat.** Tutorial machines that require invoked
   child machines, external services, or ECMAScript behavior beyond the
   current iState Rust generator's portable subset MUST be represented as
   blocked with an explicit reason until the generator boundary supports
   them.

## 9. Frozen Decisions - Testing

1. **Generated-machine vectors.** Each admitted machine MUST have vector
   tests that run with `cargo test --manifest-path <machine>/Cargo.toml`.
2. **App-level tests.** The Tutorial Demo App MUST have unit tests for:
   selector order, selected-machine switching, event dispatch, and visible
   state summary updates.
3. **Simulator smoke.** The disco simulator or host simulator MUST expose
   enough automation to select each required machine and dispatch at
   least one event to it.
4. **Workspace isolation.** Generated Tutorial Machine packages MAY be
   excluded from workspace-wide clippy if generated code style is not
   idiomatic, but their vector tests MUST remain directly runnable.

## 10. Reconciliation vs. Adjacent Repo Primitives

| Primitive | Relationship |
|---|---|
| `rlvgl-app-disco-demo` | SCTD reuses the icon-strip position and may factor reusable selector code later. It does not alter disco-demo behavior in SCTD-01. |
| Softoboros iState MCP codegen | SCTD's generation authority. The implementation vendors Rust artifacts produced through MCP rather than invoking a local generator from rlvgl. |
| `examples/stm32h747i-disco/disco-demo-states` | Precedent for generated package layout and vector verification. SCTD creates separate tutorial-machine packages instead of folding examples into this crate. |
| `docs/app-schema/04-state-machine-boundary.md` | SCTD reuses compatible vendored-package concepts where useful, but iState MCP owns generation. If compatibility filenames or manifest fields change, app-schema must be amended separately. |
| `vendor/scjson/tutorial` | Upstream read-only source. Any SCTD-normalized SCXML or transcoded asset must cite the source path and reason for normalization or transformation. |
| Lucide asset pipeline | Supplemental source for selector and utility icons when tutorial assets are absent or unsuitable. Existing disco-demo icons can be reused only when their meaning is clear for the tutorial machine. |

## 11. Non-Goals

- No local rlvgl SCXML generator is admitted in SCTD-01; generation goes
  through iState MCP.
- No runtime SCXML editing or visual state-chart editor is included.
- No attempt to implement every tutorial example in the first phase.
- No board bring-up work for targets that cannot already mount rlvgl app
  payloads.
- No changes to the existing disco demo's selector semantics.
