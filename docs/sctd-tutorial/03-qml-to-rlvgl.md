# Chapter 3 — The QML screen → a Rust widget tree

**←** [Chapter 2 — Converting the media assets](02-media-assets.md) **·** [Index](README.md) **·** [Chapter 4 — Wiring it reactive](04-reactive-wiring.md) **→**

---

By the end of this chapter you will have a generated Rust module that
constructs the Bolero media-player screen as a live widget tree — every
rectangle, label, and image from the QML source, positioned and ready to
draw. The tool that does this is the `qt emit` subcommand of
`rlvgl-creator`. This chapter uses plain Qt emission; Chapter 4 re-emits
the same screen with `--scxml-context` to add the state-machine handle and
reactive bindings.

## What `qt emit` does

```
rlvgl-creator qt emit <input.qml> <out_dir> --target rlvgl
```

Point it at a `.qml` file and an output directory and it writes a single
Rust module named `<basename>.rlvgl.rs`. That module exposes a function
called `build_screen` that constructs a live widget tree using
`rlvgl-core` and `rlvgl-widgets`. The tree is ready to draw the moment
`build_screen` returns — no separate layout pass, no stylesheet resolver,
no Qt runtime.

`--target rlvgl` is the default and the one you want for firmware or
simulator targets. There is also `--target data`, which instead writes a
static `SCREEN` constant — a pure Rust literal with no external crate
dependency in the emitted file. That mode is useful for tooling and
testing but not for a live UI; this chapter stays focused on `--target
rlvgl`.

**Directory mode.** If you pass a directory instead of a single file,
`rlvgl-creator qt emit` walks every `*.qml` file directly inside it and
emits one module per file, each named `<basename>.rlvgl.rs`. That is how
the SCTD demo generates its media-player and dining-philosophers screens
in one pass.

You do not need Qt installed. The emitter reads the `.qml` text directly;
it has its own parser and does not call into any Qt runtime.

## The QML input: `FrameMedia.qml`

The file you will be emitting from is the Bolero media-player frame that
ships with the tutorial assets. It is an ordinary Qt Quick 2 screen:

- A **root item** (`BoleroBackgroundRender`) that sets the overall
  600 × 360 canvas and clips its children.
- A **`MouseArea`** that fills the root and intercepts hover events for
  the state machine.
- Inside that, a **content padding item** that insets from all edges and
  contains the main content:
  - A **`HeaderPanel`** — the top strip with the source label and mute
    icon.
  - A **`MediaImage`** — a 160 × 160 album-art box anchored to the
    right.
  - A **`Text`** element (`textSource`) — the track name, anchored to
    fill the space to the left of the album art. Its text is
    `audioPlayer.currentPlayUrlFileName` — an external object property,
    not something defined in the QML itself.
  - A **`MediaTimeline`** — a progress bar between the album art and the
    transport controls.
  - A **`MediaFunctionKeysPanel`** — the transport button row (rewind,
    play, forward, repeat, scan, shuffle) at the bottom of the content
    area.
  - A **warning overlay** (`warningPanel`) — a scanning/error indicator
    that appears when media is unavailable.
- A **modal overlay** rectangle for dimming the screen during dialogs.
- A **`MediaBottomPanel`** — a strip anchored to the very bottom of the
  root.

Elements are positioned with QML **anchors**: `anchors.fill: parent`,
`anchors.left: parent.left`, `anchors.bottom: functionKeys.top`, and so
on. The emitter resolves all of these at emit time into concrete pixel
bounds. The generated code has fixed `Rect` values — there is no anchor
solver in the runtime.

## What the emitter produces

After running `qt emit` you get a file that opens with a header like this:

```
// Generated by `rlvgl-creator qt emit --target rlvgl` from
// `vendor/scjson/tutorial/.../FrameMedia.qml`.
// Do not edit by hand — regenerate with:
//   cargo run --features creator --bin rlvgl-creator -- \
//       qt emit --target rlvgl <input.qml> <out_dir>
```

The "do not edit by hand" instruction is important. The generated file is
a build artifact, the same way a `.pb.rs` from protoc is. If you need to
change the layout or add a widget, change the `.qml` source and
re-run the command. Editing the generated Rust directly means your change
disappears the next time you regenerate, and the emitter's internal
consistency guarantees — anchor resolution, asset symbol linking, binding
list construction — no longer apply.

Three provenance constants follow the header:

```rust
pub const QT_EMIT_VERSION: u32 = 22;
pub const QT_IR_VERSION: u32 = 2;
pub const QT_SOURCE: &str = "vendor/scjson/tutorial/.../FrameMedia.qml";
```

`QT_EMIT_VERSION` is the emitter's internal shape version. If the emitter
changes the generated API in a way that requires consumer updates, this
number increments so you can grep for it. `QT_SOURCE` records which file
was the input, so you always know where to look when the generated code
needs to change.

### How QML elements map to Rust widgets

The emitter lowers each QML element type to a corresponding widget from
`rlvgl-widgets`:

| QML element | Generated widget |
|---|---|
| `Rectangle`, root container | `Container` with a background colour |
| `Text` | `Label` |
| `Image { source: "…" }` | `Image` with pixels decoded from an RLE blob |
| `Button`, `MouseArea` (tap target) | `ClickArea` with a recorded tag |

QML **anchors** are fully resolved at emit time. A `anchors.bottom:
functionKeys.top` in the source becomes a fixed `Rect` in the generated
code — no anchor solver runs at draw time. For sibling-relative anchors
like this one, the emitter works through a topological ordering of
elements within each container so that every referenced element's size is
known before the elements that depend on it are resolved.

### The `build_screen` function

The central product of the generated module is:

```rust
pub fn build_screen(
    bounds: Rect,
) -> (WidgetNode, Rc<RefCell<ScreenState>>, Vec<LabelBinding>)
```

Pass in the `Rect` you want the screen to occupy — the content area of
your display — and you get back:

- **`WidgetNode`** — the root of the widget tree. Call `.draw(renderer)`
  on it to paint the whole screen.
- **`Rc<RefCell<ScreenState>>`** — a handle carrying the root-level QML
  property values (spacing constants, panel heights, per-button state
  flags). Most consumers do not need to touch this directly.
- **`Vec<LabelBinding>`** — static property/text bindings that can be
  refreshed after you mutate the generated `ScreenState`.

The tree is fully self-contained: `build_screen` allocates every widget,
resolves every anchor, and decodes every image asset in one call. It does
not construct the SCXML machine yet; that four-value return shape appears
only after Chapter 4 adds `--scxml-context`.

### Image assets in the generated code

Every `Image { source: "…" }` in the QML becomes an `Image` widget whose
pixels come from the RLE blobs you produced in Chapter 2. The generated
code refers to them through a `qt_assets` module:

```
qt_assets::IMG_IMGPLAY_48          ←  Qml/Images/ImgPlay_48.png
qt_assets::IMG_IMGPAUSE_48         ←  Qml/Images/ImgPause_48.png
qt_assets::IMG_IMGREWINDBACK_48    ←  Qml/Images/ImgRewindBack_48.png
qt_assets::IMG_IMGREWINDFORWARD_48 ←  Qml/Images/ImgRewindForward_48.png
qt_assets::IMG_IMGMEDIANOREPEAT_48 ←  Qml/Images/ImgMediaNoRepeat_48.png
qt_assets::IMG_IMGMUTE             ←  Images/ImgMute.png
qt_assets::IMG_IMGBOLEROBACKGROUND ←  Images/ImgBoleroBackground.png
... and several more
```

The naming convention is `IMG_` followed by the file stem uppercased and
sanitized. If you add an image to the QML, regenerate the module, and
the corresponding `qt_assets` symbol does not exist yet, the build will
tell you exactly which blob to produce in Chapter 2's pipeline.

Magenta (`0xFF, 0x00, 0xFF`) is the transparency sentinel in the RLE
format: at decode time those pixels become fully transparent. This is how
icon glyphs sit correctly over the Bolero background photo without a
rectangular white box behind them.

## Consuming the generated module

The generated file is plain Rust. Add it to your project as any other
module — either check it in directly or write a `build.rs` that
regenerates it before compilation. In the reference demo it lives at
`examples/apps/sctd-demo/src/media_player_gen.rs` and is declared as
`mod media_player_gen;` in the crate root.

Here is the non-reactive construction — building the tree and drawing it
once:

```rust
use rlvgl_core::widget::Rect;

let content_area = Rect { x: 0, y: 0, width: 720, height: 480 };

// Build the widget tree. The three return values are the tree,
// the property-state handle, and the label-binding list.
// For a static first look, only the tree matters.
let (node, _state, _label_bindings) = media_player_gen::build_screen(content_area);

// Draw it — this paints every widget to your renderer.
node.draw(&mut renderer);
```

That is enough to put the Bolero screen on your display. The background
photo appears, the transport buttons are in place, labels are positioned,
and the icons are decoded and drawn.

The reference demo's `MediaPlayerSkin` wrapper in
`examples/apps/sctd-demo/src/media_player_skin.rs` uses the Chapter 4
variant of the generated module. It still calls `build_screen`, stores the
returned node, and calls `node.draw` on each frame, but it also keeps the
returned machine and reactive bindings so the play icon flips to pause
when you tap, the mute icon appears and disappears, and the repeat button
cycles through its three states.

## Where things stand

At this point, the screen is static. You can see the whole layout — the
transport row, the mute icon in the header, the repeat and shuffle
buttons, the source-caption label, the album art placeholder — but nothing
changes. Tapping the play button does not swap the icon. The state machine
from Chapter 1 is not part of this generated module yet.

That is the one remaining piece: connecting the machine's output (which
states are active?) to the widget tree's appearance (which artwork should
be shown?), and connecting taps on the tree to machine input events. The
generated `Vec<Binding>` is the mechanism, and `--scxml-context` is what
produces it. Chapter 4 covers both.
